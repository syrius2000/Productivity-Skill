# QMS品質判断の基礎

このReferenceは、通常の状態確認や定型操作では読まない。品質基準の解釈、Evidence分類、比例的な厳格さ、人的誤操作、最終裁定の境界で判断が必要な場合だけ参照する。

## 8つの原則

1. 品質基準とリスク許容は人間Ownerが決める。
2. 判定は要求とEvidenceへ追跡できる形にする。
3. 不確実性を隠さず、未確認を成功または失敗へ補完しない。
4. 確認の厳格さはリスク、重要度、複雑性、不確実性に比例させる。
5. `fix-submitted`ではなく、有効性確認後に完了を判断する。
6. handoffは受領、理解、応答まで閉じる。
7. 人の誤りは非難せず、必須入力、Role、revision、確認で無害化する。
8. AIは助言、実行、検証を担えるが、最終リスクは人間Ownerへ戻す。

## 判定語彙

- `evidence-gap`: 判断に必要なEvidenceの種類または範囲が不足しているFinding。
- `unverified`: 対象を必要な方法で確認できていないEvidenceまたは検証結果。
- `failed`: 要求違反を直接観測または再現した結果。環境不足には使わない。
- `fix-submitted`: 修正提出の事実。有効性確認、受入、クローズを意味しない。
- `improvement-proposal`: baseline外の改善案。受入を妨げず、対応を強制しない。

## 判断境界

- Reviewerは要求を増減せず、要求外の良い案を改善提案へ分離する。
- ImplementerはFindingを変更せず、反論するときも要求参照とEvidenceを示す。
- Ownerだけがbaseline、実装許可、追加サイクル、残余リスクを裁定する。
- 同じモデルでもRole Invocationが別で、対象提出を独立に再確認できれば独立性を補助できる。別モデルであることだけでは独立性を証明しない。
- Evidenceの量ではなく、出所、対象revision、方法、結果、完全性、反証可能性を評価する。

## 読込後も行わないこと

- 規格準拠、validation完了、リリース可否を本Referenceだけで宣言しない。
- 比例性を理由にOwnerの要求や適用される必須要件を引き下げない。
- 規格解説、互換性、配備、計測機能を初期版の実行契約へ追加しない。

詳細な学習背景と一次資料は、必要に応じてリポジトリ内の関連Artifactを参照する。通常の案件処理では追加の背景資料を読まない。
