## 段階A：複数文書を一つの有用な記録へ集約する

### 実装仕様

既存の4工程を「対象選定→集約案と操作計画→承認後の作成・検証→承認範囲の反映」として維持する。

対象一覧は既存7列の実表を本文に置く。根拠欄には完了根拠と集約先を記載し、復元情報欄には文書別のコミットまたは退避先を記載する。未確認は空欄にせず未確認とする。

| 判断 | 統合後の規則 |
|---|---|
| 基本単位 | 同じ案件・目的で、一緒に読むことで経緯と結論を理解できる完了文書群を一つの集約候補とする |
| 既定動作 | 同じ案件の計画・実装報告・検証報告は、一つのサマリーへまとめる案を最初に作る |
| 日付差 | 段階ごとの完了日が違っても統合可能。全体の対象期間と必要な出来事の日付を保持する |
| 復元先の差 | 文書別の復元先を対応表へ残せるなら統合可能。不明な文書は移動・削除対象から保留する |
| 分割条件 | 独立した目的・読者・アクセス制約、または一つにすると意味や判断が混ざる具体的な理由がある場合だけ分ける |
| 保護 | 未承認・進行中・ユーザー編集中・参照中の文書は現行どおり操作候補から除外。依頼が「全部」でも自動的に解除しない |

集約本文は「対象と結論」「確定した決定と理由」「主要成果と検証の限界」「未解決事項と引継ぎ」「元文書と復元情報」の5節を基本とする。同じ事実は一度だけ記載する。古い判断が更新された場合は最終判断と更新理由を残し、単に両方を並べない。根拠が矛盾して最終判断を決められない場合は未解決として残す。

元文書の各重要な決定・未解決事項が集約先のどの節に残ったか、検証用の対応表で確認する。全文連結や、元文書1件につきサマリー1件の出力は既定にしない。

SQL表は、粒度、JOIN基数、フィルタ・NULL、集計・ウィンドウの4行を基本とする。例えばJOIN行は「JOINがある→キーの一意性と結合前後の粒度を確認し、行数増加が集計へ与える影響を示す」とする。実行承認は条件表の一行に埋めず、常時有効な安全境界に置く。
